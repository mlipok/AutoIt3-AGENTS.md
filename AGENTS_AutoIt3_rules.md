# AutoIt3 rules

Use the AutoIt executables listed in `AGENTS_AutoIt3_local_Installation.md`.

## Exclusions from inspection

Apply the following exclusions within the directory containing this `AGENTS_AutoIt3_rules.md` file and all its subdirectories:

- Do not inspect files matching `*_stripped.au3`; these are generated by AU3Stripper.exe.
- Do not inspect files matching `* copy.au3` or `*-copy.au3`, including equivalent names in the native language of the Windows environment, such as the Polish `* kopia.au3` or `*-kopia.au3`.
- Do not inspect files matching `*.au3.bak`; these are backup files generated by tools such as grepWin.
- Do not inspect any subdirectory named `BackUp`, including all of its contents; these directories contain backup files generated by tools such as Tidy.exe.
- Do not inspect files matching `*test*.au3`; treat them as experimental scripts that do not require analysis.

Match these patterns without regard to letter case. Apply the exclusions when searching for references, analyzing dependencies, reviewing code, and making changes.

## AutoIt code validation

Keep all `*.au3` source files in the repository in **UTF-8 without BOM** (the file must not start with `EF BB BF`) and use CRLF line endings. For every change, check the encoding before saving, after saving, and after running formatting tools; if an edited file has a BOM, remove it when saving. Do not replace UTF-8 with UTF-16. The `$FO_UTF8_NOBOM` constant controls how `FileOpen()` reads or writes data files; it does not replace checking the encoding of the `*.au3` source file itself. This rule does not expand the scope of files permitted for a given task.

After preparing or modifying any `*.au3` code, run these tools in order:

1. `Tidy.exe` — format the code.
2. `Au3Check.exe` — check syntax and errors with:
   `-d -w 1 -w 2 -w 3 -w 4 -w 5 -w 6 -w 7`.

Run `Tidy.exe` only with an explicit path to an existing, specific `.au3` file, passed as its sole argument as documented by this installation's SciTE `au3.properties`. Do not add `/q`. Never run `Tidy.exe` without a file path or with `/?`, even to test the program, check its invocation syntax, display help, or diagnose a problem. These invocations can open an interactive file-selection window and leave a `Tidy.exe` process running. Determine how to invoke it from documentation or existing valid invocations, without launching `Tidy.exe` in this way.
After running `Tidy.exe`, check that its process has exited. If a file-selection window appears, close it and ensure that no orphaned `Tidy.exe` process remains.

If `Au3Check.exe` fails to start with a DLL relocation or process-launch error in the restricted Codex environment, retry the same command outside that environment using `Au3Check.exe`. Record the tool path, version, execution context, and actual error and warning counts. Never report a launch failure as a syntax-check result. Check dependent modules through their public include entry point when a standalone check lacks required declarations.

If the file uses an AutoIt3Wrapper directive, use exactly:

```autoit
#AutoIt3Wrapper_Au3Check_Parameters=-d -w 1 -w 2 -w 3 -w 4 -w 5 -w 6 -w 7
```

In the change report, state the results of both checks, including all errors and warnings. If either tool could not be run, say so explicitly in the report.

Changes limited solely to the color, size, or position of interface elements do not require GUI tests. Do not run a GUI test only to confirm such changes. Still run `Tidy.exe` and `Au3Check.exe` for modified `*.au3` files. If program behavior also changes, verify that behavior to the extent needed.

## Running and compiling AutoIt scripts

`Tidy.exe` and `Au3Check.exe` do not execute the script. Run or compile a script only when the task requires its behavior or build to be verified, and only after both checks have been run.

Run a script with `AutoIt3.exe` or `AutoIt3_x64.exe` using `/ErrorStdOut` as the first argument, followed by an explicit path to an existing `.au3` file. Without `/ErrorStdOut`, a fatal error opens a modal message box and the process does not exit until that box is closed. Never run the interpreter without a script path; this opens a `Run Script:` file-selection window.

The AutoIt executables are Windows GUI programs. A shell that starts one directly can return immediately, before the script has finished, with no output and no exit code. Start the process in a way that waits for it and captures its output, for example by piping the output in PowerShell or by using `Start-Process -Wait -PassThru`. `ConsoleWrite()` writes to stdout and `ConsoleWriteError()` writes to stderr. The exit code is the value passed to `Exit`. A fatal error writes the file, line, and message to stdout and ends with exit code 1; because a script can also end with `Exit 1`, read the output before reporting the cause.

Before running a script, check it and its includes for anything that waits for a user: `MsgBox()` without a timeout, `InputBox()`, file and folder selection dialogs, a GUI message loop, `#RequireAdmin`, or a loop with no exit condition. Do not start such a script unattended. Set a time limit for every run. If the limit is exceeded, terminate only the process you started, identified by its process ID, and report the run as timed out, not as a result. Do not terminate other `AutoIt3.exe` processes; they may belong to the user. After each run, check that the process you started has exited.

Run `Aut2exe.exe` or `Aut2exe_x64.exe` only with `/in` pointing to an existing `.au3` file and with an explicit `/out` path. Without arguments it opens its interactive window, and a missing input file opens a modal `Aut2Exe Error` window. Exit code 0 from Aut2Exe confirms only that an output file was written; it also compiles a script that calls an undefined function. Never report a successful compilation as a syntax check.

In the change report, state the exact command, the exit code, and the relevant output of each run. If a script was not run, say so and give the reason.

## Scripts that act on the desktop or the system

A script started by the interpreter runs in the user's desktop session with the user's rights. It is not isolated from open windows, the keyboard and mouse, the file system, or the registry. Before running any script, inspect it and the includes it uses for calls of the following kinds:

- Simulated or blocked input: `Send()`, `ControlSend()`, `MouseClick()`, `MouseClickDrag()`, `MouseMove()`, `MouseWheel()`, `BlockInput()`, `HotKeySet()`.
- Windows and processes the script did not create: `WinClose()`, `WinKill()`, `WinSetState()`, `WinActivate()`, `ProcessClose()`.
- System state: `Shutdown()`, `RegWrite()`, `RegDelete()`, `EnvUpdate()`.
- Files and directories outside the working directory of the task: `FileDelete()`, `FileMove()`, `FileRecycle()`, `FileRecycleEmpty()`, `DirRemove()`, `DirMove()`.
- Other programs: `Run()`, `RunWait()`, `RunAs()`, `ShellExecute()`.

This list is not exhaustive; `DllCall()` and COM objects can have the same effects.

Do not run a script that can reach such a call unless the user has explicitly approved that run. When asking, name the calls and what they act on. Approval covers the script as it was inspected; ask again if those calls or their targets change. If approval is not given, limit verification to `Tidy.exe` and `Au3Check.exe` and state in the change report that the behavior was not run.

## AutoIt function headers, UDF development, and best coding practices

- Before creating or reviewing a UDF, also check `AGENTS_AutoIt3_Best_coding_practices.md` for guidance on function use, variable names and scope, initialization, constants, Au3Check directives, magic numbers, and `#include-once`. Treat its guidance as recommendations; follow the specific repository rules in this file where they differ.
- When writing, reviewing, or calling AutoIt functions, check `AGENTS_AutoIt3_Function_notes.md` for function values, optional parameters, return values, `@error`, and `@extended`. If a called function reports failure through `@error`, check that flag immediately before relying on its return value.
- Before writing or reviewing an AutoIt function header, check `AGENTS_AutoIt3_UDF-spec.md`, especially **Functions → Headers** and **Internal use only**. The source page is marked as a work in progress; where it differs from the repository-specific rules below, follow these rules.
- Use a `; #FUNCTION#` block for public functions and a `; #INTERNAL_USE_ONLY#` block for helper functions. Keep the standard field layout used in this repository: `Name`, `Description`, `Syntax`, `Parameters`, `Return values`, `Author`, `Modified`, `Remarks`, `Related`, `Link`, `Example`.
- Keep `Description` concise. In `Parameters`, explain the meaning of arguments, default values, and `ByRef` where these affect use of the function. The header must match the actual signature and execution paths.
- Use `Modified` to name people who helped modify the function. Do not put dates, change descriptions, or version history there.
- In `Return values`, describe the actual values returned on success and failure. Where the function makes this distinction, use `On Success - ...` and `On Failure - ... and sets @error ...`. Do not force this split on functions that merely preserve a received `@error` or return a Boolean without setting their own error state.
- Document `@error` codes in that function's `Return values`, not in `Remarks` or in a combined list under another function. A single code may appear on one line; list multiple codes on separate lines with their meanings. Include only codes that the function actually sets or propagates.
- If a function propagates `@error` and `@extended` from another function, say so in `Return values` and identify the source. Explain `@extended` when it carries information useful to the caller. Do not assign a helper function's error codes meanings they do not have in the public function.
- Use `Remarks` for behavior, limitations, and the meaning of states—for example, whether COM accepting a command confirms that a document was actually displayed. Do not move lists of `@error` codes there.

Example for a function with several error codes:

```autoit
; Return values .: On Success - 1.
;                  On Failure - 0 and sets @error to one of the following:
;                    1 = Invalid input.
;                    2 = Unavailable GUI.
;                    3 = Operation failed.
;                  @extended contains the underlying error when available.
```
